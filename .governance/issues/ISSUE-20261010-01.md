## 问题定义

- 用户可见现象: 读取一个本地两分钟技术视频，需要另写 Rust runner、Whisper shell wrapper、补帧和导出脚本；升级模型须另建缓存目录；最终质量依赖代理手工兜底。
- 错误日志/失败命令: 原对话的 small ASR 输出包含“卵生”等错误和音乐段重复；本轮隔离复现换成不存在的新模型仍返回旧转写；重复截帧返回两个同路径记录且 height=0；stderr 压力用例超时后子进程仍存活。
- 触发条件: Linux 无桌面环境、本地视频含技术静态图和无旁白后半段、更换模型或启用 VAD、重复/边界时间戳、生成便携图文资料。
- 当前行为: CLI/MCP 依赖 Tauri 包；MCP 视觉接口只读取 visual_proxy.mp4；缓存不校验有效 ASR 配置；本地平台硬编码 bilibili；导出只写文字及空 images 目录；子进程顺序排空 stdout/stderr。
- 期望行为: 从官方无 GUI 入口完成诊断、转写、全片视觉采样、指定时间补帧、便携素材包导出；真实来源、处理配置和覆盖范围可追溯；失败明确且可重试。

## 为什么修改

- 直接原因: 原会话完成了交付，但绕行脚本只保留在临时目录，没有进入工具的正常入口。
- 根因: 桌面与自动化入口耦合；媒体身份与处理配置身份混用；转写优先设计未贯通视觉链路和图文导出；子进程和作业退出清理不足。
- 不修改的影响: 下一次视频仍需重新编写辅助代码，且可能将旧转写、错误平台、缺失画面或占位尺寸当作新分析结果。
- 必要性: 用户明确要求依据完整对话优化 GitHub 视频阅读工具及实际痛点。
- 未采用的替代方案及原因: 不再保留第二套独立 runner；不把所有视频固定套用 120 秒时间表；不静默删除疑似重复语音；不自动编造技术解释；不引入 Word/ROS/机器人业务依赖。
